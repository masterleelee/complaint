# ISS-AP-01 · 后端：归档面板错误分级（契约冻结）

**Status:** ready-for-agent
**Priority:** P0（阻塞后续全部前端工作）
**依赖:** 无（本单先做，产出契约给 02/03/04 用）
**并行:** 可与 02/03 并行前的唯一前置

## 现象 / 需求

现在 `archive-files` 系列失败时只返回 `{"success":false,"errors":[...]}`，前端无法区分两种完全不同的原因：

- `root_unavailable`：归档共享盘未挂载 / 配置不可用 → **用户无能为力，要找管理员**
- `dir_missing`：该学员尚未生成登记表/回复函 → **用户自己能解决（去生成文档）**

混在一条提示里，用户看到的是「无法创建归档根目录…Permission denied」（程序员语言），既看不懂又误导。

## 改动点

1. `app.py` 的 `api_tickets_archive_files`（L3942-3976）、`api_tickets_archive_file_download`（L3979-4005）：
   失败分支统一返回 `jsonify({"success": False, "code": resolved["code"], "errors": [...]}), status`，
   其中 `code ∈ {"root_unavailable","dir_missing"}`，status 沿用现有映射 `{root_unavailable:400, dir_missing:404}`。
   - **注意**：`_err()` 目前不支持带 code（`app.py:217`），本单**不要改 `_err` 的签名**（全局 80+ 处调用），
     在这两个路由里直接 `jsonify` 构造，或新增一个局部 helper `_err_code(msg, code, status)`。
2. `services/archive_service.py` 的 `resolve_case_dir()`：**不加不改**，其返回的 `code` 已是所需值——本单只是把它透传到 HTTP 层。
3. 错误文案分级（放在 `archive_service.py` 的 `resolve_case_dir` 内部更合适，前端只做展示）：
   - `root_unavailable` → 「归档共享盘暂时不可用（可能未挂载），请联系管理员，或稍后重试」
   - `dir_missing` → 「该学员尚未生成投诉登记表 / 回复函，请先在工单里生成后再查看」
   - 保留原始技术细节在 `errors` 数组里（不删），便于排查，但前端只展示人话。

## 验收标准

- [ ] `GET /archive-files` 在夹子缺失时返回 `{"success":false,"code":"dir_missing",...}` + 404
- [ ] `GET /archive-files` 在根目录不可用时返回 `{"success":false,"code":"root_unavailable",...}` + 400
- [ ] `download` 与后续 `zip`/`preview` 三个端点共用同一套 code 语义
- [ ] `pytest tests/test_archive_files_api.py tests/test_open_archive_api.py -v` 全绿（既有断言若依赖旧错误体，一并更新）
- [ ] 新增用例：两个 code 各至少 1 例（可 mock `resolve_case_dir`）

## 风险

- **中**：改动会触碰既有 9 例测试的断言（错误体从 `error` 键变成 `code`+`errors`）。必须先跑一遍基线测试确认现状，再改。
- **低**：`_err()` 不动 → 无全局连锁。
