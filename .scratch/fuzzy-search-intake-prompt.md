# 实施提示词：新增投诉页「统一智能查询 + 学员模糊查找」

> 用途：交给 AI Agent 或开发者直接实施的完整任务说明。
> 编写日期：2026-08-23。基于原型 demo/fuzzy_intake_v2.html 与现有代码结构编写。

---

## 一、背景

学员投诉处理系统（Flask + Vue3，单页模板 `templates/index.html`）。现流程：受理员在「新增投诉」页必须填写身份证号或手机号才能查询三系统并建案。

现实问题：投诉来电经常只知道 **学员姓名 + 报名点 + 大概报名时间**，不知道手机号和身份证号。需要支持用这些信息到内部系统做模糊查找，人工确认学员后一键进入现有精确查询流程。（第三系统经实测不支持姓名检索，见 3.6。）

## 二、目标

在「新增投诉」页提供一个**统一查询入口**：用户有什么填什么，系统自动选择查询路线：

```
输入优先级：身份证号 > 手机号 > 姓名(模糊)
├─ 有身份证号        → 精确路线（现有逻辑，零改动）
├─ 无证件号、有手机号 → 精确路线 by phone（现有逻辑，零改动）
└─ 只有姓名(+报名点+时间范围) → 新增模糊路线（轻量）：
     1. 查内部系统（name/orgid/sjlx=1+日期范围，已实测可行）
     2. 命中 → 返回候选列表（轻量字段）
     3. 用户点候选行的「投诉处理」→ 回填证件号/手机号 → 复用现有
        「查询三系统并建案」异步流程（含东莞驾培合同检查）
```

## 三、功能需求

### 3.1 页面布局调整（② 登记投诉信息卡）

1. **工单属性组上移**：放在学员身份查询区的上面。理由：来源渠道/投诉日期/投诉类型基本是默认值，用户先扫一眼即可。保持紧凑（两列网格）。
2. **学员身份组改造为统一查询区**，一行排布：
   - 身份证号（原样）、手机号（原样）、学员姓名（新增）、报名点/分校（新增，下拉数据来自现有 `GET /api/organization-units`，默认「全部报名点」）、报名时间起止（新增，两个 date 输入，可留空=不限）。
3. 主按钮文案动态：
   - 填了证件号或手机号 → 「查询三系统并建案」（现状行为不变）
   - 只填了姓名 → 「搜索学员」

### 3.2 查询路由规则（前端 useComplaint.js）

| 条件 | 行为 |
|------|------|
| id_card 非空且格式有效 | 忽略其他条件，走现有 `/api/query/start`（证件号精确） |
| id_card 空，phone 为 11 位 | 走现有 `/api/query/start`（手机号精确） |
| 两者皆空，name 非空 | 调新接口 `POST /api/students/search`，展示候选表 |
| 全空 | 报错「请填写查询条件」 |

### 3.3 模糊查询（后端，轻量）

- **只查内部系统的分页列表接口**，参数：`name` + `orgid`(选) + `sjlx:"1"`+`queryStartTime`/`queryEndTime`(选)；不触发时间轴(`queryXySjz`)、收费(`queryXySfList`)、考试次数分析 —— 目的是秒级返回。
- 无结果 → 返回空列表，前端仅显示「未找到匹配学员」，**不要**出现"放宽条件/未录入系统"之类的建议文案。第三系统姓名检索 API 复现不稳定（见 3.6），不做 fallback，仅依赖内部系统。

### 3.4 候选列表展示与「投诉处理」

- 表格列：选择 | 姓名 | 身份证号(脱敏) | 手机号(脱敏) | 报名点 | 车型 | 报名日期 | 当前进度 | 操作。
- 脱敏在前端做：身份证 `前4***…***后3`，手机 `前3****后4`；手机号旁「显示」链接点击才显示全文。
- **最后一列「投诉处理」按钮**：点击后把该行 `id_card`、`phone` 回填表单，立即复用现有 `queryAllAndGo()` 流程（`POST /api/query/start` → 轮询 `/api/query/status/<job_id>`），进入三系统精确查询+建案，自动跳工作台。
- 同名多人靠 报名点+报名日期+进度+欠费徽标 人工分辨。
- 候选超过50条时（`total>50`，如只输单字姓"陈"会命中6291人）：表格上方提示「共X条匹配，仅显示前50条，请补充报名点或报名时间」，不自动翻页。

### 3.5 一致性提醒

精确查询返回后，若以下情况出现，在结果上方显示一条黄色轻提醒（不阻断流程）：
- 所填手机号 ≠ 系统登记手机号：「⚠ 系统登记手机号为 158\*\*\*\*0340，与你所填不同」
- 居留证被自动补全前缀（现有 `F` 前缀逻辑）：「⚠ 已按补全后的证件号 F1249468(8) 查询」

### 3.6 外部接口实测结论（T0 已完成，2026-08-23）

**内部系统 `POST /sypro_jm/xyxxController/listXyxx.action` —— 模糊查找可行 ✅**
参数即网页版搜索表单字段名（已从 index.jsp 表单 `app_yxgl_xygl_searchForm` 与 JS `app_yxgl_xygl_searchFun()` 确认），全部可空：

| 参数 | 说明 | 实测 |
|------|------|------|
| `name` | 学员姓名 | ✅ 服务端过滤。**包含匹配**（LIKE %x%："陈"命中6291人含"齐陈强"；全名精确唯一命中） |
| `orgid` | 分支机构代码（如 kj002） | ✅ 有效，错误值返回0行 |
| `sjlx` | 日期维度开关，**必须传 `"1"` 日期过滤才生效** | ✅ 已证实：无 sjlx 时日期被忽略；sjlx=2 返回空body；sjlx=3 也可用（含义未明，固定用 1） |
| `queryStartTime` / `queryEndTime` | 报名时间范围，格式 `yyyy-MM-dd` | ✅ 配合 sjlx=1 生效（2030范围→0行，报名当年范围→命中） |
| `page`/`rows`/`sort`/`order` | 分页排序，同现有爬虫 | ✅ |

实现要点：
- 组合查询统一带 `sjlx:"1"`。
- 单字姓名会命中数千人（total=6291）：固定 `rows≤50`，响应里带回 `total`；前端当 `total>50` 时提示「共X条，请补充报名点/报名时间」。
- 不调用时间轴/收费/考试分析接口（轻量）。

**第三系统 `xyxxAction!list.action`（网页学员查询）—— 姓名框存在，但 API 复现不稳定 ⚠️**
- 网页表单 `yycxForm` 确有姓名框，字段名 `ksyyXyxx.xm`，提交到 `/xyxx/xyxxAction!list.action`。
- 实测（在数据齐全的爬虫账号会话）：按 `ksyyXyxx.sfzmhm` 可命中目标学员；但按 `ksyyXyxx.xm=陈金生` 无法命中（真实名/假名返回长度几乎相同，均不含目标学员证件号），改 GBK 编码重发仍无效。
- 原因推测：`list.action` 表单含 `rep.reportKey`/`rep.dataSourceParams`，走**报表框架**；纯 POST 姓名缺报表上下文时不生效（需先建报表条件）。这是 headless API 复现的难点。
- 结论：**模糊查找只依赖内部系统**（它本就是全量学员主数据源）。内部系统命中即得证件号 → 现有精确流程照常查第三系统（计时学时）与驾培系统（电子合同）。**不实现"内部无结果→查第三系统"的 fallback**；若日后确需，需另立项逆向报表框架。

## 四、改动清单（按文件）

| 文件 | 改动 |
|------|------|
| `crawlers/internal.py` | 新增 `search_students(name, org_code="", date_from="", date_to="", limit=50)`：复用 `listXyxx.action`，传 `name`+`sjlx:"1"`(+orgid/日期范围) 替代 `sfzh`，循环 `_parse_student_row()` 解析全部命中行并带回 `total`；**不调用** `_get_timeline/_query_fees/_analyze_timeline`。登录态失效重试沿用现有模式 |
| `app.py` | 新增路由 `POST /api/students/search`（同步轻接口，超时 15s）。入参校验：name 必填非空。响应含 `source:"internal"`、`candidates[]`、`total`、`elapsed_ms` |
| `templates/index.html` | ②卡片重排：工单属性上移；学员身份区加姓名/报名点/时间范围输入；候选结果表 + 「投诉处理」按钮 + 空结果文案；一致性黄条提醒 |
| `static/js/composables/useComplaint.js` | 新增 `fuzzySearch()`、`pickCandidate(i)`（回填+调 `queryAllAndGo()`）；`queryAllAndGo` 入口处加路由判断（3.2 表格） |

不改动：`/api/query`、`/api/query/start`、`core/query_engine.py` 合并逻辑、`services/intake_service.py`、案件工作台。

## 五、接口契约

```
POST /api/students/search
请求: { "name":"陈金生", "org_code":"", "date_from":"2025-01-01", "date_to":"2025-08-01" }
响应: {
  "source": "internal",
  "total": 1,
  "candidates": [ {
    "name":"", "id_card":"", "phone":"",
    "license_type":"", "school_name":"", "school_short":"",
    "registration_date":"", "student_status":"", "exam_stage":"",
    "is_owed": false
  } ],
  "elapsed_ms": 912
}
错误: 400 name为空；500 含 sources 说明哪个系统失败
```

## 六、验收标准

1. 填身份证号 → 行为与现在完全一致（回归不破坏）。
2. 只填手机号 → 走手机号精确查（现有）。
3. 只填姓名+报名点+时间 → ≤2s 返回候选表；候选行点「投诉处理」→ 触发三系统进度条 → 建案成功进工作台。
4. 查无结果 → 仅显示「未找到匹配学员」，无多余建议文案。
5. 工单属性显示在学员身份区上方。
6. 模糊请求的后端日志中不出现 queryXySjz/queryXySfList 调用（证明轻量）。
7. 手机号不一致时出现黄色提醒。

## 七、约束

- 最小改动，遵循各文件现有代码风格；不加注释性废话。
- 所有新文案中文，与现有 UI 术语一致（"报名点"、"建案"、"三系统"）。
- 涉及外部系统参数的假设一律先验证再编码（见 3.6）。
