# 多 Agent P0 交付设计

**日期：** 2026-07-04  
**状态：** 已获业务方向确认，待书面复核  
**目标：** 在不重写技术栈、不扩大 v1 范围的前提下，修复会造成错查学员、错误扣费、非法完结和敏感信息泄露的 P0 问题，并建立可重复的交付机制。

## 1. 底层原则

本项目首先是投诉案件决策系统，不是普通查询页面。正式输出必须满足四个不变量：

1. 学员身份必须精确匹配，外部系统故障不得解释为“查无此人”。
2. AI 只提取合同事实，正式扣费只能由后端唯一规则引擎计算。
3. 已确认费用方案必须形成不可被普通更新或重新分析覆盖的正式快照。
4. 案件完结、回复函和飞书归档必须读取同一份正式案件快照。

性能优化必须建立在结果正确的基础上。禁止为了缩短等待时间缓存不完整结果、模糊选择第一条学员记录或跳过人工确认。

## 2. 交付组织

### 2.1 产品与交付 CEO

由主线程承担，拥有最终优先级、范围、合并和签收权。

职责：

- 将业务规则转化为可验证的不变量。
- 为每项任务指定唯一文件所有者。
- 阻止 Agent 扩大范围、重写技术栈或覆盖其他人的修改。
- 只有在需求审查、代码审查和测试验收全部通过后才签收。

### 2.2 专业负责人

| 角色 | 责任 | 无权执行 |
|---|---|---|
| 业务规则负责人 | 核对费用口径、六类结果、回复函和归档闸门 | 直接修改生产代码 |
| 架构负责人 | 维护模块边界、依赖方向和迁移顺序 | 发起技术栈重写 |
| 三系统负责人 | 身份匹配、错误语义、缓存、超时和登录态 | 改变业务费用口径 |
| 安全隐私负责人 | 路径、TLS、配置、权限、日志和敏感信息 | 删除正式业务档案 |
| 测试发布负责人 | 金标准、API、E2E、性能和恢复验收 | 降低验收标准以迁就实现 |

### 2.3 程序员与审查员

每个开发任务使用独立程序员 Agent，并按 TDD 执行。完成后依次分配：

1. 需求符合性审查 Agent：只判断是否完整实现任务、是否增加未要求功能。
2. 代码质量审查 Agent：检查正确性、安全性、可维护性和回归风险。
3. 测试发布 Agent：运行专项测试与全量回归。

同一任务的程序员不得兼任审查员。

## 3. 目标架构

继续使用 Flask + Vue 3 + SQLite 单体，不引入微服务、FastAPI、ORM、Redis 或 Celery。

### 3.1 唯一费用规则模块

新增 `core/refund_engine.py`，提供纯函数接口：

```python
calculate_fee_plan(contract_facts, progress_facts, manual_overrides) -> fee_plan
```

约束：

- 合同总额、实交金额和扣费项目必须是有限非负数。
- 明细合计必须等于总扣费。
- 总扣费不得超过规则允许的上限。
- 方梓林案例固定为应扣 1726 元、应退 1554 元。
- 前端只能展示草案并提交结构化人工调整，不能产生正式金额。

### 3.2 案件工作流模块

新增 `core/case_workflow.py`，集中处理：

- `confirm_fee_plan`
- `complete_case`
- `reopen_case`
- `official_snapshot`

所有普通更新、合同重新分析、回复函和飞书入口都必须服从该模块的不变量。

### 3.3 三系统查询接口

保留当前并发查询结构，将每个系统结果规范为：

```text
found / not_found / auth_error / timeout / upstream_error / parse_error / ambiguous_identity
```

约束：

- 身份证必须精确匹配。
- 手机号只有在内部系统唯一匹配到身份证时才能继续。
- 禁止在精确匹配失败时使用第一条记录。
- 包含错误、超时或关键详情缺失的结果不得作为完整缓存。

### 3.4 合同证据链

合同文件分为：

- 不可变原件
- OCR 或视觉模型使用的派生文件
- 用户预览文件
- 结构化合同事实
- 人工确认后的费用快照

任何压缩、合并和 OCR 都不得覆盖原件。磁盘文件名使用服务端生成的不透明 ID，姓名和身份证只进入数据库字段。

## 4. 交付批次

### 批次一：财务与案件正确性

- 封锁普通更新、重新分析和旧接口对 confirmed 费用的覆盖。
- 建立后端唯一费用规则。
- 修复 `actual_paid`、负数、NaN、扣费明细与汇总不一致。
- 建立六类结果和统一完结闸门。
- 飞书不得直接修改案件状态。

验收：不存在绕过确认或完结闸门的 API；方梓林金标准通过；已确认快照不可被覆盖。

### 批次二：查询正确性

- 三系统精确身份匹配。
- 区分无记录和系统故障。
- 手机号多匹配返回人工处理。
- 禁止缓存部分失败结果。
- 修复闰年日期异常。

验收：错误学员自动选择率为 0；故障误报“查无此人”为 0。

### 批次三：合同与安全边界

- 原件不可变、派生文件可追踪。
- 所有文件路径使用真实路径包含校验。
- 配置限制可修改字段和允许的模型主机。
- 恢复 TLS 校验、日志脱敏和本地文件最小权限。

验收：目录跳转、兄弟目录、符号链接、越权图片和恶意模型地址全部拒绝；日志不出现完整身份证、手机号或 Key。

### 批次四：真实样本与端到端

- 为 `合同文件/` 中每组合同建立人工确认金标准。
- 使用方梓林真实照片完成上传、提取、确认和计算。
- 覆盖受理、查询、合同、费用、沟通、归档、回复函和历史恢复。
- 覆盖桌面 1440×900 和手机 390×844。

验收：核心流程成功，浏览器控制台错误为 0，正式金额误差不超过 0.01 元。

### 批次五：性能和运行可靠性

- OCR 预热、分层识别和低置信度二次识别。
- 查询 deadline、会话隔离、在途请求合并和指标。
- 数据库连接生命周期、任务过期清理、配置原子更新。
- 锁定真实依赖并建立备份恢复流程。

验收：三系统健康查询总耗时 p50 不超过 5 秒、p95 不超过 8 秒；失败任务不阻塞后续查询；恢复演练 RPO 为 0。

## 5. 每项任务的质量闸门

每个任务必须依次通过：

1. **RED：** 新增最小失败测试并确认因目标缺陷而失败。
2. **GREEN：** 用最小代码使专项测试通过。
3. **需求审查：** 不缺需求、不增范围。
4. **质量审查：** 无 Critical 或 Important 问题。
5. **回归：** 全量 pytest、Python 编译、JavaScript 语法检查通过。
6. **业务验收：** 对应真实样本或 API 场景通过。

任一闸门失败，任务退回原程序员修复，禁止带病进入下一批。

## 6. 工作区与变更策略

当前 `codex/case-workbench` 分支存在大量未提交的历史修改。执行前必须先建立可恢复的基线，不能从旧 `HEAD` 创建一个遗漏现有实现的工作树。

策略：

1. 盘点并保存当前变更基线。
2. 只提交明确属于当前项目的现有修改，不夹带缓存、密钥和运行数据。
3. 从该基线创建隔离工作树或由 Agent 使用独立 fork。
4. 并行程序员只能修改互不重叠的文件集合；共享核心文件任务必须串行。

## 7. 明确不做

- 不增加 v1 退款执行、退学申请表和账号权限产品功能。
- 不重写前端页面或更换 UI 框架。
- 不让 AI 直接决定正式扣费。
- 不自动删除正式案件和合同原件。
- 不为了“覆盖率数字”编写源码字符串断言。
- 不以当前 98 项测试通过作为发布结论。

## 8. 发布判定

只有以下条件全部满足才允许从 `NO-GO` 改为 `GO`：

- 五个交付批次的 P0 验收全部通过。
- 真实合同金标准全部有明确结果或明确人工复核原因。
- 所有正式输出读取同一 confirmed 快照。
- 桌面和手机核心 E2E 通过。
- 全新环境可安装、启动和测试。
- SQLite、配置和业务文件完成备份恢复演练。
- 测试发布负责人和产品与交付 CEO 双方签收。
