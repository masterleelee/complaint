## 一、执行摘要

**本系统的三系统查询，核心目的是「身份解析」——把姓名/手机号解析成身份证号。不是拿学时，也不是拿缴费。**

身份证件号一旦拿到，才能解锁后续链路：驾培电子合同查询（费用的真正来源）→ 合同分析 → 退费计算 → 归档出表。查不到证号，整条链路就停摆。

测试学员甲就是卡在这里：内部系统无档案、手机号反查失败 → 拿不到证号 → 后续全断。而她的证号明明存在于第三系统，只是系统没有"按姓名问第三系统"这条路。

### 业务口径（`templates/index.html:1457` 官方说明）

> 基本信息以内部系统为准；**实操学时取审核有效学时**；**合同与收费记录来自东莞驾培平台**

代码事实与之完全吻合：

| 数据项 | 真实来源 | 消费点 |
|---|---|---|
| 合同 / 收费 / 监管金额 | **东莞驾培** `driving_fee` | `app.py:2733`、`:3603-3616`、`index.html:1483-1494` |
| 实操培训费判断 | `training_hours` 中的**科目二** | `contract_service.py:1051`（`"二" in ... and subject_key == "subject2"`） |
| 内部系统收费记录 | `internal._query_fees` | **无任何下游消费点**（仅 `internal.py:490` 自产自销） |

> 由此明确：**科目一学时无用**（口径是实操学时，且只看科目二）；**内部系统/第三系统的缴费无用**（收费来自驾培）。

### 2.3 姓名匹配口径：**全名精确匹配**（2026-08-30 复核修正）

初版判断为「前缀匹配」，复核后**已证伪**。用身份证反查交叉验证后确认：

| 输入 | 命中身份证数 | 说明 |
|---|---|---|
| `测试学员甲` | 1 | 全名命中本人 `110101199003070011` |
| `张振` | 3 | **3 名真实姓名就叫「张振」的学员**：`110101199003070011` / `110101199003070011` / `110101199003070011`。已用这三个证件号反查，姓名列取值均为 `张振`，证明姓名列就是全名、不随查询词截断 |
| `振苹` | 0 | 不支持包含匹配 |
| `张` | 0 | 单字无效 |

**关键推论**：`张振` 命中的是同名同姓的**其他人**，既不是前缀也不是包含，而是**全名精确匹配**。
「同名歧义」的本质随之从「前缀串味」变为「**真实重名**」——去重后 >1 个身份证即需人工挑选。

> 必须传完整姓名（≥2 字），结果**按身份证去重**，>1 个转人工候选。

### 2.3.1 分页能力缺失（本次新增发现）

服务端**单页硬上限 10 行**，且 `pageNumber` / `pagesize` 两个参数均被忽略：

| 请求 | 数据行 | 去重身份证 |
|---|---|---|
| `张振` + `pagesize=10` | 10 | 3 |
| `张振` + `pagesize=50` | 10 | 3 |
| `张振` + `pageNumber=2` | 10 | 3（与第 1 页完全相同） |

> 后果：常见姓名（如「张伟」）的候选会被截断且无法翻页。实现以 `truncated=True`
> 显式告知上游「名单可能不完整」，并在前端给出提示，不做静默截断。

### 2.4 测试学员甲闭环数据

- **身份证：`110101199003070011`**（`validate_id_card` 合法）。4 个阶段行全部指向同一证号，无同名歧义。
- 三系统可见性：**内部 `None` / 驾培 `None` / 第三系统命中** —— 属真实数据缺口（2017 年老学员）。
- **P0 可行性已验证**：`third.query_student("110101199003070011")` 走现有生产路径**直接命中**。

### 2.5 自动降级分支不可达（实测复现）

```
_empty_result 返回 {internal: not_found, third: not_queried, driving: not_queried}
  → classify_match_result 判定 outcome = "undetermined"
  → 前端要求 outcome === "no_match" 才降级
  → 条件恒 false → 不调用 searchStudents()
```

对照组：若把 third/driving 标成 `not_found`（即 `QUERY_PLAN.md:104` 写法）→ `outcome = "no_match"` → **降级反而触发**。标对（not_queried）卡死，标错反而通。

## 四、目标边界

### 做什么

只动**查询编排层**，目标是让"姓名"和"回填证号"成为可用的身份解析入口。

- `crawlers/third.py` —— 加姓名查询入口（**只取身份证 + 姓名**）
- `app.py` 查询编排 —— 降级逻辑、新增 requery 端点
- `useComplaint.js` / `useWorkbench.js` —— 降级闸门、工作台入口
- 文档与状态语义

### 不做什么（明确红线）

| 不动 | 原因 |
|---|---|
| `driving_fee` / 驾培合同链路 | 费用真正来源，动它直接影响退费金额 |
| `services/contract_service.py` | 合同分析与退费计算核心 |
| 归档、登记表、回复函生成 | 与本次查询编排无关 |
| 第三系统学时解析 | **科目一学时无用**；实操学时口径以驾培为准 |
| 内部系统 `_query_fees` 的删除 | 仅列为 P3 优化项，不纳入本次（涉及既有性能预期） |

### 第三系统姓名查询只取什么

**只解析身份证号与姓名**，不解析 4 个培训阶段的学时/里程。理由：学时对投诉系统无用途（口径是驾培实操学时，且只看科目二）。

## 六、对现有流程的影响评估

现有系统**能正常运行**，只是查询不完美。以下是逐项影响评估：

| 改动 | 影响等级 | 说明 |
|---|---|---|
| `third.py` 加 `name=None` 参数 | **零影响** | 纯新增可选参数，现有调用不传 → 走原路径，分支不进入 |
| `third.py` 解析器条件过滤（1.5） | **低风险（唯一需回归）** | 现有身份证查询走同一函数。**缓解：仅在身份证为空时才启用新分支，有证号时代码路径逐字不变** |
| `app.py` 新增 `phone_not_found` 字段 | **零影响** | 纯新增返回字段，老前端忽略即可 |
| 前端降级闸门（1.2） | **低风险** | 仅改变"手机号查无"场景的 UI 走向，不影响查询与落库 |
| 新增 requery 端点（2.1） | **零影响** | 纯新增 API，不触碰 `/api/query`、`/api/query/start` |
| requery 落库白名单（2.5-2.7） | **零影响** | 只 patch 白名单，`save_ticket` 对已有 id 本就是部分 UPDATE |
| 批次 3 UI 语义（3.1） | **中风险** | 改变状态展示，需回归受理页与工作台 |
| 批次 4 改库（4.1-4.3） | **需单独确认** | 直接改数据，须先备份 |

### 结论

**批次 1 与批次 2 对现有流程实质影响为零到低**：全部是"新增入口"或"新增可选参数"，不修改任何现有代码路径的行为。唯一的例外是 `third.py:133/166` 的解析器改造，必须靠验收项 2（身份证查询结果与改造前完全一致）把关。

**批次 3 起才触及既有展示逻辑**，届时建议单独回归。

### 必须守住的回归底线

1. 有身份证的查询路径，行为与改造前**逐字一致**（测试学员甲证号可作基准用例）
2. 投诉内容、附件、处理记录在任何重查后**不丢失**
3. 已归档工单不被重查破坏（2.1 已设拒绝）
