### 2.2 三档风险分级

**🔴 现在就会炸（1 项）**

`contract_service.py:588` `makeup_count`。已用真实调用复现：

```
contract_set_from_ai_data({total_fee:5000, includes_makeup_fee:False,
                           makeup_fee_table:{subject2:200}}, source="local_rules")
  → 通过（0 条规则）        ← 本地规则路径，短路不崩
contract_set_from_ai_data({total_fee:5000, makeup_fee_table:{subject2:200}})
  → NameError: name 'makeup_count' is not defined   ← AI 路径，必崩
```

触发链路：`contract_set_from_ai_data`（L528-611）是两条路径的**公共函数**，L574 `includes_makeup = bool(data.get("includes_makeup_fee", True))` 缺省为 `True`。本地规则路径在 L508 硬编码 `includes_makeup_fee: False` 因而被 `and` 短路；AI 路径（`_bool_from_contract(..., True)`，L967）为 `True`，只要 LLM 从合同里识别出补考费金额（`makeup_fee_table` 非空）就抛 NameError。

**为什么至今没爆**：`makeup_fee_table` 只可能来自 LLM 提取（前端无补考费录入字段，L926 本地规则返回空表）。也就是说——**合同里一旦出现可识别的补考费条款，AI 合同分析即失败**。补考费是驾培合同常见条款，属于高频触发面。

修复量：1 行（对照 L1021–1023 的正确实现 `makeup_count = max(0, count - 1)`，或按注释"次数由规则引擎从内部系统考试次数计算"补取数逻辑）。

**🟡 现在不炸，接上就炸（2 项）**

| 项 | 现状 | 触发条件 |
|----|------|---------|
| `/api/tickets/<id>/communications` | `templates/index.html` 已无对应 UI，`useWorkflow.js:1053/1075` 触发不到 | 谁把"沟通记录"卡片加回工作台，一加就 404 |
| `/api/tickets/<id>/fee-reopen` | `reopenFeePlan`（useWorkflow.js:1206）已被 return（:1414）且 `app.js:199/861` 已解构，但模板没绑按钮 | 加一个按钮就 404（后端只有 `fee-unlock`） |

这两项本质是"**接了一半的线**"——后端拆了、前端没清，或前端写了、后端没有。当前不可达，不构成现实风险，但会误导后来人。

**🟢 完全不影响使用（其余全部）**

死代码、死端点、空表、仓库垃圾、CSS 重复定义等，删与不删对运行时行为**零影响**。它们的真实成本是：

### 2.3 一个需要留意的脆弱点

`app.py:4463` 在模块顶层调用 `create_default_template()`，失败时仅 `system_logger.error` 一行，**fail-silent**。默认模板是回复函生成的依赖——若该表或模板缺失，启动时不会有任何显性提示，故障会延迟到"生成回复函"那一刻才暴露（正如 21:41 那两条 ERROR 所演示的）。

### P0-1 `services/contract_service.py:588` — `makeup_count` 未定义  ✅ **已于 2026-08-30 修复**

```python
if includes_makeup and makeup_count > 0 and makeup_fee > 0:   # NameError
```

**已实证复现**（直接调用，非静态推断）：

```
contract_set_from_ai_data({total_fee:5000, includes_makeup_fee:False,
                           makeup_fee_table:{subject2:200}}, source="local_rules")
  → 通过（0 条规则）
contract_set_from_ai_data({total_fee:5000, makeup_fee_table:{subject2:200}})
  → NameError: name 'makeup_count' is not defined
```

- `makeup_count` 在 `services/contract_service.py` 全文件**只出现于 L588 这一行**；L1021 那个同名变量属于 `_parse_ai_response`（L909-1082）的局部变量，与本处无关。L573 注释写着"次数由规则引擎从内部系统考试次数计算"——原本打算赋值，漏了。
- `contract_set_from_ai_data`（L528-611）是**两条路径的公共函数**：L616 本地规则、L636 AI 都会调到它。
- L574 `includes_makeup = bool(data.get("includes_makeup_fee", True))` —— **缺省 `True`**。
  - 本地规则路径：L508 硬编码 `includes_makeup_fee: False` → `and` 短路 → 不崩。
  - AI 路径：L967 `_bool_from_contract(..., True)` / L924 均为 `True` → **不短路**，只要 `makeup_fee_table` 有金额即抛异常。
- `makeup_fee_table` 只能来自 LLM 提取（L969）。前端无补考费录入字段，本地规则路径 L926 返回空表 —— 这正是 210 个测试全绿的原因。
- **现实触发面**：补考费是驾培合同常见条款，AI 一旦识别到金额即失败。

**修复方案（已实施）**：删除越权的 `makeup_count > 0` 判断，改为与考试费规则对称的 `if includes_makeup and makeup_fee > 0:`。三重依据：

1. **同函数考试费规则**（L579）为 `if includes_exam and exam_fee > 0:` —— 不判断次数；
2. **同模块人工复核版** `contract_set_from_reviewed_fields`（L702）为 `if includes_makeup and makeup_fee > 0:` —— 同样不判断次数，证明 AI 版是多写了一个条件；
3. **下游** `core/refund_engine.py:592–624` 消费 `makeup_fee` 规则时自行计算 `makeup_count = max(attempts - 1, 0)` 并处理 `count == 0`。

即本函数产出的是「**单次金额**」规则模板，次数应由下游结合三系统考试次数折算，此处判断次数既无数据来源也属越权。代码内已留注释说明，防止后人改回。

**回归测试**：新增 `tests/test_contract_makeup_fee_rule.py`（9 项）。反向验证有效——把代码改回 bug 版本后该测试文件 **7 failed / 2 passed 且复现 NameError**，恢复后 9 项全过。

**验证结果**：AI 路径 + 补考费 → 正常生成 `科目二补考费 amount=200.0`；本地规则路径（硬编码 `includes_makeup_fee=False`）行为不变，仍不生成补考费规则。

> ⚠️ **需重启服务才生效**：`app.py` 以 `app.run(host="0.0.0.0", port=5003)` 启动，无 debug/reloader，运行中的进程仍加载旧代码。
