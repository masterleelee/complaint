# 学员投诉处理系统 PRD

版本：2026-07-09

状态：v1 产品基线。旧版根目录 DRD 保留为历史参考；发生冲突时，以本文档和 `docs/acceptance/v1-requirements-matrix.md` 为准。

## 1. 产品目标

本系统用于把学员投诉处理从“人工查系统、人工翻合同、人工算退费、人工归档”收敛为可复核的案件工作台。

核心目标不是让 AI 直接替人下结论，而是：

1. 快速识别学员线索并查询三系统。
2. 自动获取或上传合同原件。
3. 用模板规则和 AI 提取合同字段。
4. 用后端规则引擎生成可审计费用草案。
5. 由处理人确认阶段性或正式费用方案。
6. 记录沟通、结果、回复函和归档材料。
7. 按经营单位统计有效投诉量、撤销量和处理情况。

## 2. 产品边界

v1 覆盖投诉案件从受理到归档的信息闭环。

v1 不做：

- 退款付款执行。
- 财务审批流。
- 退学申请表签字回收流。
- 复杂账号、角色、权限体系。
- 分校/分店退费金额统计。
- 让 AI 直接生成可对外使用的金额结论。

## 3. 标准流程

1. 投诉受理：上传、粘贴或录入投诉材料。
2. 线索识别：自动提取身份证号和手机号，不用大模型扩写完整投诉事实。
3. 三系统查询：身份证优先；仅手机号时先通过内部系统查身份证。
4. 案件补全：处理人补充投诉日期、来源、类型、事实简述、处理人。
5. 合同获取：优先下载东莞驾培电子合同；无电子合同时上传 PDF、图片或扫描件。
6. 合同字段提取：模板规则优先，大模型兜底。
7. 规则扣费草案：后端根据合同字段和已查询事实计算。
8. 费用方案确认：处理人确认阶段性方案或正式方案。
9. 沟通记录：保存多轮联系、学员意向和后续动作。
10. 最终结果：从固定六类中选择。
11. 文档生成：按需生成回复函、登记表或阶段性说明。
12. 归档与统计：归档材料，更新有效投诉量和经营单位看板。

## 4. 状态模型

状态必须拆成四个维度，不允许用单一状态混合表达。

| 维度 | 选项 | 用途 |
|---|---|---|
| 案件处理状态 | 待处理 / 处理中 / 已完结 | 表示案件流程进度 |
| 费用方案状态 | AI草案 / 阶段性方案 / 正式方案 | 表示金额结论能否对外使用 |
| 最终结果 | 六类固定结果 | 表示投诉处理结论 |
| 归档状态 | 未归档 / 已归档 / 归档失败 | 表示材料是否沉淀完成 |

最终结果固定为：

1. 投诉撤销
2. 同意合同扣费
3. 不同意合同扣费但协商一致
4. 不同意合同扣费且协商失败
5. 无法联系
6. 继续培训/转校

## 5. 三系统权威口径

| 数据 | 权威来源 | 说明 |
|---|---|---|
| 姓名、身份证、手机号、报名时间、主学习进度、经营单位归属 | 内部系统优先 | 内部系统有信息时，不需要第三系统辅助归属 |
| 科二/科三实操学时 | 第三系统 | 只用于实操费计算，不反推主学习进度 |
| 电子合同 | 东莞驾培系统 | 只用于合同原件，不参与经营单位归属 |
| 内部系统无经营单位 | 第三系统可作为兜底 | 仍需在界面标记来源 |
| 系统都无法给出经营单位 | 人工选择或填写 | 未填写前显示未知 |

三系统数据不完整是正常情况。缺一个系统不等于案件不可处理。系统按已查到事实计算，并显示数据来源不足。

学习进度口径：

- 内部系统状态是主进度，如报名、科二收、科三收、已领证。
- 第三系统学时只用于科二/科三实操费。
- 只有合同、没有内部系统进度时，系统不得自动判断学习阶段，需处理人选择。
- 学员未到考试阶段时，考试次数和实操学时按 0 处理，不视为错误。

## 7. 统计口径

统计重点是案件数量和处理质量，不统计退费金额。

| 指标 | 口径 |
|---|---|
| 投诉工单数 | 所有真实投诉工单，包含撤销 |
| 有效投诉量 | 排除投诉撤销、重复导入、误建 |
| 撤销量 | 最终结果为投诉撤销的工单数 |
| 重复投诉 | 同一身份证多次投诉单独展示 |
| 时间口径 | 默认按投诉日期 `complaint_date` |
| 分校/分店排行 | 默认按有效投诉量排行，可切换投诉工单数和撤销量 |
| 金额统计 | 不做 |

撤销口径：

- 学员明确撤销，或主管部门/转办方通知撤销，才算投诉撤销。
- 撤销工单不计入有效投诉量。
- 撤销工单仍保留在案件列表和学员历史中。
- 撤销工单可完结归档，不强制费用方案和回复函。
- 重复导入、误建不是撤销，应作为数据错误排除。

撤销记录应保存撤销日期、撤销来源和撤销说明/证据。

## 8. 合同分析原则

合同分析采用“模板规则优先，大模型兜底”。

| 合同类型 | 处理策略 |
|---|---|
| 东莞驾培文字层 PDF，已知模板 | 本地规则秒级解析，不调用大模型 |
| 东莞驾培新模板 | 增加对应本地解析器 |
| 扫描 PDF / 图片 / 纸质合同 | 图像增强 + 视觉模型 + 关键区域裁剪 + 人工确认 |
| 本地规则解析失败 | 调用大模型结构化提取 |
| 大模型输出 | 只能作为候选字段，进入人工确认 |

AI 的职责是提取字段、条款、候选值和证据片段；正式金额结论由规则引擎计算，并由处理人确认。

## 9. 合同数据模型

一个案件必须支持多份合同。一份合同是一等公民，不允许把多份合同压成一个总额字段。

每份合同至少包含：

| 字段 | 说明 |
|---|---|
| contract_id | 系统内部合同 ID |
| title | 合同名称 |
| source_file | 原件路径 |
| total_fee | 该合同总额 |
| rules | 扣费规则列表 |
| evidence | 条款证据或原文片段 |
| missing_pages | 缺页列表 |
| missing_fields | 缺失字段 |
| warnings | 提醒项 |
| blockers | 阻止正式确认的问题 |

每条扣费明细必须保存：

| 字段 | 说明 |
|---|---|
| contract_title | 来自哪份合同 |
| item | 扣费项目 |
| amount | 金额 |
| clause | 合同条款依据 |
| trigger | 触发事实 |
| formula | 计算公式 |
| evidence | 原文证据 |

## 10. 费用计算口径

### 10.1 实际已交金额

- 默认实际已交金额 = 合同总培训费。
- 多份合同默认实际已交金额 = 各合同总额之和。
- 合同中的“东莞驾培平台支付金额”“第三方存管金额”等属于学员已交学费的一部分，只是支付方式说明。
- 系统不得把平台支付金额当作独立退款基数，也不得用它覆盖合同总培训费。
- 分期未付、优惠、减免、欠费、补缴、额外收费等特殊情况，由处理人手动调整实际已交金额并填写原因/证据。

### 10.2 考试费、补考费、工本费

| 场景 | 规则 |
|---|---|
| 合同明确包含考试费/补考费/工本费 | 从该合同资金池扣 |
| 合同明确不含、另行支付 | 不从该合同扣，除非有单独代收合同 |
| 存在代收代交考试费合同 | 从该合同按已发生考试/补考扣 |
| 合同没写清楚 | 默认包含，但提示人工确认 |
| 未到考试阶段 | 考试费和补考费按 0 |
| 已考某科 | 扣该科首次考试费 |
| 同一科多次考试 | 第一次扣考试费，后续按补考费 `次数 - 1` |
| 工本费 | 只有已领证/科四完成，或合同触发条件满足时才扣 |

### 10.3 违约金

| 场景 | 规则 |
|---|---|
| 合同明确写违约金比例 | 按该合同总额乘以比例 |
| 合同明确写固定违约金 | 按固定金额 |
| 多份合同各有违约金 | 各算各的 |
| 某份合同没有违约金条款 | 不扣违约金 |
| AI 没识别到违约金 | 不默认 20%，只提示未识别 |
| 手写/补充条款疑似违约金但模糊 | 提醒人工确认，不自动扣 |

### 10.4 三年有效期

- 合同有效期起算使用三系统报名时间，内部系统报名时间优先。
- 不从合同图片或文本中识别签署日期作为有效期计算依据。
- 超过三年但合同未明确写到期不退时，只提醒，继续正常计算。
- 超过三年且合同明确写期满不退/终止不退时，该份合同应退金额置 0。
- 多份合同中只有一份到期不退时，只影响该合同。
- 报名时间缺失时提醒人工补录，不自动判定不退。

## 11. 模糊字段处理

系统要尽可能自动识别手写金额、勾选项和模糊字段，但不能硬猜成正式依据。

自动识别顺序：

1. 整页视觉大模型识别。
2. 图像增强后重识别。
3. 关键区域裁剪识别，重点是金额区、退费条款区、勾选区、手写备注区。
4. 仍不确定时，展示候选值、局部截图和置信说明，由处理人确认或补录。

涉及金额、日期、补充条款的模糊字段，未确认前不能进入正式费用方案。不影响金额的签名、盖章模糊只提醒。

## 12. 费用方案状态与版本

| 状态 | 用途 |
|---|---|
| AI草案 | 系统自动生成，内部参考，不可直接对外 |
| 阶段性方案 | 处理人快速确认，可用于主管部门进展回复，须标明初步核算 |
| 正式方案 | 沟通和材料相对完整后确认，用于最终回复函、归档和对外结论 |

确认后修改规则：

- 已确认方案默认锁定。
- 发现错误时，处理人必须点击重新打开费用方案并填写修改原因。
- 修改前版本保留为历史，新版本重新确认。
- 回复函已生成后再修改金额时，系统提示回复函金额已过期，需要重新生成。
- 已归档后允许更正，但必须记录更正原因和更正前后金额。

## 13. 文档生成规则

只要文档里出现应扣、应退、不退等金额结论，金额必须来自阶段性方案或正式方案，不能来自 AI草案。

| 文档类型 | 金额要求 |
|---|---|
| 正式回复函 | 必须使用正式费用方案 |
| 阶段性进展回复 | 可使用阶段性费用方案，并标注初步核算 |
| 撤销说明 | 不强制费用方案 |
| 无法联系说明 | 通常不写金额；如主管部门要求金额，使用阶段性方案 |
| 登记表 | 可按案件事实生成，是否带金额取决于业务需要 |

## 15. 验收门槛

v1 完成必须同时满足：

1. PRD 与验收矩阵无冲突。
2. P0 需求都有自动化测试或可复核样本。
3. 合同样本全部有期望值，或明确标记不可判定原因。
4. 三系统支持正常、无记录、部分失败、超时和人工兜底。
5. 桌面和手机都能完成受理、合同、费用、沟通、文档、归档和历史恢复。
6. 全量测试、Python 编译和 JavaScript 语法检查通过。
